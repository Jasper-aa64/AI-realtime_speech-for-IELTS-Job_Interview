# Django Migration Plan

Created: 2026-05-14

## 1. Decision

The project will move toward a Django backend, but the migration should be staged.
The current lightweight web app remains the runnable product while the Django
backend is prepared in a separate path.

This avoids mixing two risky changes:

- ongoing product/UI changes in the current app
- framework migration, database modeling, login, billing, and deployment changes

## 2. Current State

The current web app is:

- backend: `web/ielts_server.py`
- frontend: `web/static/index.html`, `web/static/app.js`, `web/static/styles.css`
- data: local IELTS JSON banks under `data/ielts/`
- reports: JSON files under `reports/`

It is not currently Django or FastAPI. It uses Python standard-library HTTP
server code.

## 3. Target Architecture

Recommended target:

```text
frontend: Vue 3 + Vite + TypeScript
backend: Django + Django REST Framework
database: MySQL-compatible database for production
cache/state: Redis
background jobs: add Celery/RQ/Django task backend only when needed
deployment: nginx + WSGI/ASGI app server
```

For the next step, the backend should be created first. Vue migration should wait
until the API contracts are stable.

## 4. Backend Module Structure

Use business app modules instead of vague utility modules:

```text
backend_django/
  manage.py
  config/
    settings/
    urls.py
    asgi.py
    wsgi.py
  apps/
    accounts/
    speaking/
    writing/
    billing/
    ai/
    common/
```

Responsibilities:

- `accounts`: users, profiles, display names, login/register.
- `speaking`: speaking sessions, turns, reports, scoring snapshots.
- `writing`: writing prompts, entries, calendar status, writing score results.
- `billing`: token wallet, ledger, pricing, payment orders.
- `ai`: AI task records, provider metadata, prompt versions, fallback states.
- `common`: shared response helpers, timestamps, ownership metadata, audit helpers.

## 5. Database First Draft

Core tables to model first:

- `User`
- `UserProfile`
- `SpeakingAttempt`
- `SpeakingTurn`
- `SpeakingReport`
- `WritingPrompt`
- `WritingEntry`
- `WritingScore`
- `TokenWallet`
- `TokenLedger`
- `PaymentOrder`
- `AITask`

Indexes to include early:

- user-owned records: `(user_id, created_at)`
- speaking attempts: `(user_id, mode, created_at)`, `(status, created_at)`
- writing entries: `(user_id, entry_date)`, `(user_id, task_type, created_at)`
- token ledger: `(user_id, created_at)`, `(wallet_id, created_at)`
- payment orders: `(user_id, status, created_at)`, unique provider order id
- AI tasks: `(user_id, task_type, status, created_at)`, `(related_type, related_id)`

## 6. Migration Phases

### Phase 0: Freeze Contracts

Document current API behavior and JSON report fields. Do not rewrite the old app.

Outputs:

- API inventory
- report field inventory
- migration mapping from JSON files to Django models

### Phase 1: Django Scaffold

Create `backend_django/` with settings split for local and production. Add app
modules, DRF, database config, health endpoint, and ownership metadata.

No old app replacement yet.

Phase 1 implementation files live under `backend_django/` and `requirements/`.
The current `web/` app remains the active product backend during this phase.

### Phase 2: Database-Bearing Legacy Data First

Add login/register foundation, user profile fields, token wallet, ledger,
payment order models, weak-item training observations, writing learner profiles,
and import tooling for existing local persistence.

Database-bearing legacy sources:

- `reports/billing/billing.sqlite3`
- `reports/training/training.sqlite3`
- `reports/attempts/*.json`
- `reports/writing/*.json`
- `reports/writing_profiles/*.json`
- `reports/billing/codex_jsonl/*.jsonl`

Import command:

```bash
python backend_django/manage.py import_legacy_data --reports-dir reports --dry-run
python backend_django/manage.py import_legacy_data --reports-dir reports
```

Real payment provider integration stays out of scope until the ledger model is
stable.

Implemented MVP endpoints in this phase:

- `POST /api/accounts/register/`
- `POST /api/accounts/login/`
- `POST /api/accounts/logout/`
- `GET/PATCH /api/accounts/me/`
- `GET /api/billing/wallet/`
- `POST /api/billing/recharge/`
- `POST /api/billing/reservations/`
- `POST /api/billing/reservations/release/`
- `POST /api/billing/settle/`

### Phase 3: Writing Migration

Move `每日写作` first because its domain is newer and simpler than the full
speaking report pipeline.

APIs:

- summary/calendar
- prompt list/random
- entry save
- entry detail
- AI score result

### Phase 4: Speaking Migration

Move speaking attempts, turns, reports, audio references, Band 7 versions, AI
coaching, and scoring snapshots.

Keep fallback states explicit:

- generated by AI
- deterministic default fallback
- missing/unavailable

### Phase 5: Optional Job Queue

Only add a dedicated queue when product behavior needs it, for example:

- long AI scoring jobs should not block requests
- ASR/TTS tasks need retries
- many users submit at the same time

Redis can be added first for cache/session/state. Celery or RQ can follow when
background processing becomes a real need.

### Phase 6: Vue 3 + Vite

After backend APIs stabilize, move the frontend to Vue 3 + Vite. Keep the first
screen as the actual practice workspace, not a marketing page.

## 7. Development Ownership

Single-threaded plan for now:

- Django migration work happens in `backend_django/` and docs.
- Current app feature changes continue in `web/` only when needed.
- Avoid editing old app internals during the scaffold stage unless a blocking
  compatibility issue appears.

If another session resumes current UI feature work later, keep its scope limited
to:

- `web/ielts_server.py`
- `web/static/*`
- current JSON data/report compatibility

The Django migration should avoid touching those files until a planned cutover.
