# IELTS 项目重构总体架构（贯穿实验 2–5）

> 目标：在**保留现有成熟浏览器产品（baseline）功能设计不变**的前提下，把「MVP + 补丁」
> 的内部实现重构成职责清晰、可测试、可部署的架构，并叠加 C++/WASM/实时链路作为**增量加速层**；
> 同时让 6000+ 行的 C++/Qt 面试系统从「旧参考」升级为产品的**实时语音加速能力**——
> 既有运行时存在感（C++ 在产品里真跑代码），也有架构血脉存在感（产品的实时能力源于这套 C++ 系统）。
> 五个实验不是五道独立题，而是**同一次「重构 + 扩展」的五个阶段**（重构现有实现，扩展加速能力，不改产品设计）。

> 角色分工：用户负责设计决策、指挥、最终验收；落地实现由执行方按本文档与实验文档进行。

> **最高原则（baseline）**：现有浏览器产品是主线，**不推倒重来**。
> P1/P2/P3/Mock、每日写作、写作/口语报告、语料库、Takeaway、账号/钱包/题库弹窗、
> 现有「浏览器录音 → 上传 → 报告生成」流程，全部**保留、不改产品设计**。
> 本文档所有 C++ / WASM / 实时链路 = **叠加在 baseline 之上的加速层 + 可降级的可选实时能力**；
> 旧批处理流程 = fallback。叙事是「在成熟系统上重构与扩展」，不是「重做一个系统」。
> ```text
> 当前成熟功能 = baseline（不改产品逻辑）
>         │ 增量增强（重构 / 抽象 / 性能）
>         ▼
> audio_core / WASM / realtime gateway  = acceleration layer
> 旧批处理流程                          = fallback
> ```

## 0. 现状诊断（为什么要重构）

### Python / Django 侧
- `apps/speaking/services.py` **5388 行**、`apps/writing/services.py` **1868 行**：上帝文件，函数职责混杂。
- `apps/ai/provider_adapters.py` 714 行：provider 选择写死在 if/elif；adapter 子类 `run()` 骨架重复；降级逻辑隐式散落。
- AI 调用全部走 `codex exec` 子进程：每次冷启 agentic CLI 进程，**追问延迟高、失败率高、且云服务器上根本没有 codex 命令——无法部署**。
- 整体有「先能跑、再打补丁」的痕迹，缺少稳定抽象层。

### C++ / Qt 侧（src/ + include/，约 6000+ 行，GTest 已存在）
真实存在且有价值的模块：

| 模块 | 行数 | 价值 | 在新架构中的去向 |
|---|---|---|---|
| `common/protocol.cpp` | 478 | 字节/openspeech 实时语音**二进制协议帧**手写编解码 | → 实时网关核心 |
| `services/realtime_client.cpp` | 543 | WebSocket 实时对话客户端（回调 + 多线程） | → 实时网关核心 |
| `ielts/realtime_speech_capture.cpp` | 268 | VAD 式语音捕获与切分 | → 抽出 `audio_core` 纯核 |
| `services/audio_manager.cpp` | 236 | PortAudio 音频 I/O（采集/播放） | → IO 层与 `audio_core` 分离 |
| `ielts/scorer.cpp` | 252 | 多后端评分（Codex/OpenAI/Claude/Heuristic） | → **现成 Strategy 模式 C++ 实例**，与 Python 侧 AIProvider 跨语言呼应 |
| `services/llm_client.cpp` | 454 | OpenAI 兼容 HTTP 客户端 | 设计参考 |

**关键洞察**：用户要做的「边说边出字（准实时）」交互，正是这套 C++ 实时语音系统（protocol + realtime_client）当年的用途。它们不是被「复活」，而是**本来就是干这个的**——产品方向升级让最硬核的 C++ 部分从遗产变成主线刚需。

## 1. 目标架构（最终形态）

```text
浏览器 (web/static)
  ├─ AudioWorklet 采音
  ├─ [C++ #1] audio_core.wasm  ── VAD / 静音裁剪 / 重采样 / 归一化 / 质检
  │     （Emscripten 编译；浏览器端预处理，上传更小更干净）
  │     ↓ 干净音频帧
  └─ WebSocket ───────────────────────┐
                                       ▼
                  [C++ #2] 实时语音网关（常驻服务, Linux 云服务器）
                     ├─ realtime_client.cpp   WebSocket 客户端
                     ├─ protocol.cpp          二进制帧编解码
                     ├─ 背压 / 重连 / 连接生命周期
                     └─ 对接 openspeech 流式 ASR
                                       ↓ 流式转写文字
                  Django（ASGI / Channels）
                     ├─ 转写落库、推文字给前端（边说边出字）
                     ├─ apps/ai：AIProvider «Strategy» ── 追问 / 评分 / 报告
                     │     ├─ HttpApiProvider  直连 OpenAI 兼容 API（低延迟，可部署）
                     │     ├─ CodexProvider    本地 Codex CLI（开发用，非部署路径）
                     │     ├─ MockProvider     确定性，测试用
                     │     └─ FallbackProvider 责任链末端，必带 metadata 标记
                     └─ 旧「录完上传 → 批处理评分」流程 ── 保留为兜底 / 降级下游
```

一份 C++ 核（`audio_core`）+ 两个壳（WASM 前端 / native 后端网关）+ 一处设计遗产（scorer Strategy）+ 一条降级链（实时失败 → 批处理兜底）。

### 三处 C++ 现身
1. **`audio_core.wasm`（前端）**：浏览器端音频预处理，真收益 = 上传体积小、后端压力低。
2. **实时语音网关（后端常驻服务）**：手写二进制协议 + WebSocket，对接流式 ASR，是「边说边出字」的发动机。
3. **scorer 的多后端 Strategy（设计遗产）**：C++ 里现成的 Strategy 模式实例，与 Python `AIProvider` 形成「同一模式、两种语言」的双语料。

### LLM 延迟/失败问题的根因与解法
- 根因：`codex exec` 是 agentic CLI，被当成低延迟推理 API 用——每次冷启进程、带 reasoning、超时重跑、还无法部署。
- 解法（实验2 Strategy 的存在理由）：补出 `HttpApiProvider` 直连 OpenAI 兼容 API（流式、持久连接、无进程冷启）；按 task_type 路由——**追问走低延迟 HTTP API + 流式**，报告可配 HTTP 或 Codex；失败快速切链而非原地重试。`provider_config.py` 已埋好 openai/claude 的 enable 开关与 secret env 名，目前只是空脚手架待填。

## 2. C++ 定位决策（已锁定）

- **角色**：C++ realtime speech gateway（常驻服务）+ browser WASM audio core；旧批处理保留为兜底/降级下游。
- **部署**：Linux 云服务器，可跑常驻 C++ 服务（用户已确认）。
- **ASR 源**：openspeech 流式 ASR（用户已确认有可用 key/服务）。
- **准实时标准**：参照语音 App 体感 = 分段流式（停顿即出这句、说完即评），不强求逐 token 全双工渲染。
- **第一锤**：抽 `audio_core`（纯函数、无 IO、无 ASR key、无长连接、本地可测）——不一上来碰最重的长连接网关。

### 实现路径（与作业报告顺序解耦）
```
① 抽 audio_core（纯核）
② 给 audio_core 加测试（GTest）
③ 接 WASM demo（Emscripten）
④ 上 C++ realtime gateway（protocol + realtime_client 重构）
⑤ Django 接入 realtime / fallback 双链路（ASGI）
```
- 报告按 2 → 3 → 4 → 5 写；实现允许**实验2 立抽象与实验4 的 C++ 抽核轻度并行**。
- 实时网关（④⑤）工程最重，地基稳后再上；旧流程全程兜底，无 deadline 压力。

## 3. 五个实验 = 一次重构的五个阶段

| 实验 | 主题 | 在本架构中的动作 | 交付物 |
|---|---|---|---|
| 实验2 | 设计模式 / 架构设计 | 设计 `AudioProcessor` / `RealtimeGateway` / `ASRProvider` / `FallbackPipeline`（C++ 侧）与 `AIProvider`（Python 侧）的**接口与类图**；Strategy / Adapter / Chain of Responsibility / Template Method 四模式讲清。**接口与类图先成立，不强求全做完** | 设计文档 + 类图 + Python 侧 AIProvider 可运行重构 |
| 实验3 | TDD | 测 `audio_core` 纯函数 + 协议解析 + Django realtime/fallback 状态切换 + provider 链。暴露并修复缺陷（如 fallback 冒充成功、切分错段、状态切换漏判） | 测试用例/脚本说明 + 缺陷与修复记录 |
| 实验4 | 重构坏味道 | 从旧 `audio_manager` / `realtime_speech_capture` / `protocol` 抽出 `audio_core` 纯核（before：IO/设备/协议/业务混杂；after：纯核 + IO 层 + 编排分层）；Python 侧拆 `speaking/services.py`、`writing/services.py` 上帝文件、消重 | before/after 对比（C++ 与 Python 两侧） |
| 实验5 | 开源复用 | C++ 重构 + **明确集成一个开源库**（WebRTC VAD / SpeexDSP / libsamplerate 三选一）+ Emscripten 编译 WASM + 浏览器实时预处理 | 下载地址 + 库原理 + 集成方式 + 集成前后对比 |

**实验5 关键修正**：「复用开源软件资源」要求的是**集成一个开源功能模块**，Emscripten 工具链本身不算复用证据。必须接一个真开源库（首选 WebRTC VAD 或 SpeexDSP），否则不满足课程要求。

## 4. 设计模式落点（实验2 细节见《实验2_设计文档.md》）

- **Strategy**：`AIProvider.run(task) -> ProviderRunResult`（Python，provider 运行时可切换）；`ASRProvider`（C++，可切换 ASR 源）；scorer 多后端（C++，现成实例）。
- **Adapter**：`HttpApiProvider`/`CodexProvider` 适配各 AI 后端；`RealtimeGateway` 适配 openspeech 二进制协议——把外部服务原始输出转成内部统一契约。
- **Chain of Responsibility**：实时链路失败 → 批处理兜底；AI provider 失败 → 备用 provider → 明确标记的 fallback。fallback 结果结构上不可能为 SUCCESS，**杜绝假装 AI 成功**（项目红线）。
- **Template Method**：评分/报告流程骨架（build prompt → 调后端 → 解析 → 包结果）提到基类，子类只填钩子。

---

## 5. 约束与红线（贯穿全程）

- follow-up / 报告必须真调用 AI；fallback 必须带 metadata 明确标记，**不得伪装 AI 成功**；不加「内容拦截器」吞 AI 输出。
- C++ 跨平台编译注意：现工程绑死 `arm64-osx` / `/opt/homebrew`；部署到 Linux x86_64 需重新处理工具链（vcpkg triplet、依赖、Emscripten SDK）。
- 不提交 `db.sqlite3`；不随意 reset/checkout。
- 不为 Web bug 去改 C++，除非本架构明确要求（audio_core 抽核 / 实时网关属明确要求）。
- 前端左侧栏比例、报告横向滚动、Windows Edge 100% 缩放等 UI 敏感点不在本架构改动范围内。

## 6. 旁线：除 C++ 外真正该优化的性能点（不混入主线，单列备忘）

来自评审讨论，确属真实性能坑，但与 C++/实时主线解耦，按需另起小任务：
1. Task 1 图片：缩略图 + WebP/AVIF + 选中再加载高清（比 JS 乱 preload 有效）。
2. 首屏请求瘦身：按页面加载，列表用 compact payload，详情再 fetch。
3. `web/static/app.js` 按模块拆分（writing/speaking/reports/corpus/takeaway）。
4. AI 全异步化：保存/开始练习/切题不等 AI，后台 worker 完成后通知 UI。
5. 报告/语料/Takeaway 列表分页或懒加载，不每次全量拉。
6. 固定 TTS（开场题、cue card instruction）预生成并缓存。
7. 数据库索引：`user+created_at`、`status`、`task_type`、`attempt_id`。

## 8. 已确认决策（锁定）

1. C++ = 实时语音网关 + 浏览器 WASM audio core；旧批处理保留兜底。
2. 部署 = Linux 云服务器（可跑常驻 C++）；ASR = openspeech 流式（key 可用）；准实时 = 语音 App 体感（分段流式）。
3. 第一锤 = 抽可测的 `audio_core`，不先碰长连接网关。
4. 实现路径 ①→⑤（见 §2）；报告顺序 2→3→4→5；实验2 与实验4 的 C++ 抽核可轻度并行。
5. 实验5 必须集成真开源库（WebRTC VAD / SpeexDSP / libsamplerate），工具链不算复用。
6. 实验2 边界：Python `AIProvider` 抽象 + C++ 接口设计**一起做，但 C++ 只到接口/类图层级**。
