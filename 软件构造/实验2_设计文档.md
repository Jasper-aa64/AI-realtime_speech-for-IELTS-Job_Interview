## 一、为什么选这条链路做模式设计

IELTS 产品里最复杂、也最痛的子系统是「AI / 语音执行链路」，且痛点是**真实的、可量化的**：

- **延迟与失败**：写作评分、口语追问、口语报告全部走 `codex exec` 子进程。`codex` 是 agentic CLI，每次冷启进程 + 带 reasoning + 超时重跑，**追问延迟高、失败率高**；且云服务器上没有 codex 命令——**无法部署**。
- **降级红线**：后端失败时需要降级，但降级结果**必须明确标记**，绝不能冒充「AI 成功」展示给用户（项目硬红线）。
- **重复**：写作评分与口语报告流程高度相似（构造 prompt → 调后端 → 解析 → 包结果），大量重复。
- **未来实时链路**：产品要做「边说边出字」，需要「实时 ASR 失败 → 批处理兜底」的可切换链路。

这正是 GoF 设计模式的典型用武之地。更关键的是：**现有代码已经长出了这些模式的雏形，只是没成形、没命名、不一致**（`provider_config.py` 甚至已埋好 openai/claude 的 enable 开关与 secret env 名，只是 `resolve_provider_route()` 只接了 codex）。本实验的工作是「把半成型的模式补完、扶正、统一」，因此 before/after 真实可对比，而非硬塞模式。

### 现状（重构前）的问题清单

| 文件 | 行数 | 坏味道 |
|---|---|---|
| `apps/ai/provider_adapters.py` | 714 | adapter 子类 `run()` 骨架高度重复；provider 选择写死在 `select_provider_adapter()` 的 if/elif；降级散落；`run_codex` 内含「json 失败再跑一次非 json」的隐藏双跑 |
| `apps/ai/provider_config.py` | 247 | 路由配置已存在（`ProviderRoute`）、openai/claude 脚手架已埋，但未和「策略选择」「降级链」打通，只接了 codex |
| `apps/ai/orchestration.py` | 227 | `succeed/fallback/fail` 三态编排与 adapter 结果之间映射手写、重复 |

## 二、四个设计模式的落点

### 模式 1：Strategy（策略）—— provider 可运行时切换（兼修延迟）

**意图**：把「用哪个后端执行任务」做成可替换的算法族，调用方不感知具体实现；并借此**为追问引入低延迟 HTTP 直连路径**。

**现状**：`select_provider_adapter(task)` 用 if/elif 把 task_type 映射到具体 adapter，只支持 codex。

**重构后**：

```
AIProvider (Strategy 接口)
  ├─ HttpApiProvider     # 直连 OpenAI 兼容 API：流式 + 持久连接 + 无进程冷启（追问主路径，可部署）
  ├─ CodexProvider       # 本地 Codex CLI（开发用，非部署路径）
  ├─ MockSuccessProvider # 本地确定性结果（开发/测试）
  └─ FallbackProvider    # 明确降级
```

- 抽象 `AIProvider`，`run(task) -> ProviderRunResult` 为唯一策略方法。
- 具体策略由 `resolve_provider_route()` 路由结果决定，而非硬编码 if/elif。
- **按 task_type 路由修延迟**：`follow_up → HttpApiProvider`（流式低延迟），`report/score → 可配 HTTP 或 Codex`。
- 切换 provider 只需改路由配置 / 环境变量，调用方零改动。

```
TaskExecutor ──uses──▶ AIProvider «interface»
                          △
        ┌─────────────┬───┴────────┬──────────────┐
  HttpApiProvider CodexProvider MockSuccessProvider FallbackProvider
```

### 模式 2：Adapter（适配器）—— 统一外部后端与外部进程

**意图**：系统要接多个异构外部物：OpenAI 兼容 HTTP API、Codex CLI 子进程、（未来）C++ 实时语音网关。各用 Adapter 把原始形态转成内部统一契约。

**现状**：`CodexWritingScoreAdapter` / `CodexSpeakingReportAdapter` 在适配 Codex，但名为「Adapter」却同时承担策略选择、流程编排，职责不纯。

**重构后**：

- `HttpApiClient`（Adaptee）：封装 OpenAI 兼容端点的流式 HTTP 调用。
- `CodexCliClient`（Adaptee）：封装 Codex CLI 子进程（现有 `run_codex` + `extract_codex_json_events` 收敛，**去掉隐藏双跑**）。
- `HttpApiProvider` / `CodexProvider`（Adapter）：实现 `AIProvider`，把各自后端原始输出适配成 `ProviderRunResult`。
- `RealtimeGateway`（Adapter，C++ 侧，**本实验只到接口**）：把 openspeech 二进制协议适配成内部转写事件流。
- 可替换性：`MockSuccessProvider`（不依赖外部）证明上层只依赖接口。

```
   HttpApiClient        CodexCliClient        RealtimeGateway(C++, 仅接口)
       │ wrapped by         │ wrapped by            │ adapts
  HttpApiProvider       CodexProvider          openspeech 二进制协议
       │ implements         │ implements
       └─────────┬──────────┘
                 ▼
        AIProvider «interface» ──returns──▶ ProviderRunResult (统一契约)
```

### 模式 3：Chain of Responsibility（责任链）—— 双层降级链

**意图**：把「主路径失败 → 降级」做成显式责任链。**降级必带明确 metadata 标记**。本架构有两层链：

1. **AI provider 链**：`HttpApiProvider →(失败)→ CodexProvider →(失败)→ FallbackProvider`。
2. **语音链路链**（设计层预留，实现属后期）：`实时 ASR 网关 →(失败)→ 批处理「录完上传评分」兜底`。

**现状**：`ProviderRunResult` 已有 `SUCCESS / FALLBACK / retryable_failure / terminal_failure / skipped` 五态，但串联是隐式的、散落在编排里。

**重构后**：链上每个处理者返回 `ProviderRunResult`：
- `SUCCESS` → 链终止，正常返回。
- `retryable_failure` → 交给链中下一个 provider。
- `FALLBACK` → 链终止，但 `outcome=FALLBACK`，**`metadata` 明确记录降级原因**。
- `terminal_failure` → 链终止，向用户暴露真实失败（不伪造 AI 结果）。

**红线落进结构**：fallback 路径在类型上不可能产出 `outcome=SUCCESS`，从结构上杜绝「假装 AI 成功」。这一条是实验三的重点测试用例。

### 模式 4：Template Method（模板方法）—— 评分流程骨架共享

**意图**：写作评分与口语报告流程骨架一致，只有「构造什么 prompt / 怎么解析结果」不同。骨架提到基类，差异下沉到钩子。

**现状**：`CodexWritingScoreAdapter.run()` 与 `CodexSpeakingReportAdapter.run()` 结构几乎一样，代码重复。

**重构后**：

```python
class AiTaskTemplate(AIProvider):           # 模板方法基类
    def run(self, task) -> ProviderRunResult:   # 固定算法骨架
        prompt = self._build_prompt(task)        # ← 钩子
        raw = self._client.invoke(prompt, ...)   # 后端由具体 client 决定
        if 失败: return self._on_failure(...)     # ← 进入责任链下一环
        payload = self._parse_payload(raw, task) # ← 钩子
        return ProviderRunResult.success(payload, metadata=...)

    def _build_prompt(self, task): ...      # 子类实现
    def _parse_payload(self, raw, task): ...# 子类实现

class WritingScoreProvider(AiTaskTemplate): ...   # 只填两个钩子
class SpeakingReportProvider(AiTaskTemplate): ... # 只填两个钩子
```

- 消除写作 / 口语两条路径重复 → **天然成为实验四「重构消重」的素材**。

### 2.5 三个补充抽象（接口设计，实验2 只到签名/类图）

本实验除上面四个核心模式落点外，还需把以下三个抽象的**接口签名**定下来，作为后续实现与
C++/Python 跨语言呼应的契约。它们分别对应「实时语音链路」「报告流水线」「二进制协议」。

#### ASRProvider（Strategy，C++ + Python 呼应）
可切换的 ASR 源抽象，让「openspeech / 其他云 ASR / 本地 whisper」运行时可替换。

```cpp
// C++ 侧接口（仅头文件级，实验4/5 实现）
struct AsrChunk { std::string text; bool is_final; int64_t start_ms; int64_t end_ms; };
class ASRProvider {                              // Strategy 接口
public:
    virtual ~ASRProvider() = default;
    virtual void Start(const AudioFormat& fmt) = 0;          // 建立会话
    virtual void PushAudio(const int16_t* pcm, size_t n) = 0;// 流式喂音频
    virtual void OnResult(std::function<void(AsrChunk)>) = 0;// 转写回调（流式）
    virtual void Finish() = 0;                                // 收尾
};
// 具体策略：OpenSpeechAsrProvider / (未来) WhisperLocalAsrProvider
```

```python
# Python 侧对应（设计层，与 C++ 呼应；Django 通过网关消费转写事件）
class ASRProvider(Protocol):                     # Strategy 接口
    def start(self, fmt: AudioFormat) -> None: ...
    def push_audio(self, pcm: bytes) -> None: ...
    def on_result(self, cb: Callable[[AsrChunk], None]) -> None: ...
    def finish(self) -> None: ...
```

#### ReportPipeline（Template Method）
口语报告 / 写作报告共享的生成流水线骨架。是模式4（Template Method）在「报告」维度的具体化，
与 `AiTaskTemplate` 同源——`AiTaskTemplate` 管单次 provider 调用骨架，`ReportPipeline` 管
「收集材料 → 调用 AI → 组装分段复盘 → 落库」的更高层骨架。

```python
class ReportPipeline(ABC):                       # Template Method 基类
    def generate(self, ctx: ReportContext) -> Report:   # 固定骨架
        material = self._collect_material(ctx)      # ← 钩子
        ai_result = self._run_ai(material)          # 复用 ProviderChain（责任链）
        if ai_result.is_fallback:                   # 红线：fallback 明确标记
            return self._assemble_fallback(ai_result, material)
        return self._assemble_report(ai_result, material)  # ← 钩子

    @abstractmethod
    def _collect_material(self, ctx): ...
    @abstractmethod
    def _assemble_report(self, ai_result, material): ...

class SpeakingReportPipeline(ReportPipeline): ...   # 口语：turns/transcript/分段
class WritingReportPipeline(ReportPipeline): ...    # 写作：原文/AI 写法/AI 辅导
```

#### ProtocolAdapter（Adapter）
openspeech 实时语音的二进制帧编解码接口，从现有 `protocol.cpp`(478 行) 抽出契约。
`RealtimeGateway` 依赖此接口，与「连哪家 ASR 的具体帧格式」解耦。

```cpp
class ProtocolAdapter {                           // Adapter 接口
public:
    virtual ~ProtocolAdapter() = default;
    virtual std::vector<uint8_t> EncodeAudioFrame(const int16_t* pcm, size_t n) = 0;
    virtual std::vector<uint8_t> EncodeTextQuery(const std::string& text) = 0;
    virtual ParsedResponse DecodeFrame(const uint8_t* data, size_t n) = 0;
};
// 具体实现：OpenSpeechProtocolAdapter（复用现有 protocol.cpp 的帧逻辑）
```

## 三、四个模式如何协同（依赖闭环）

```
Template Method  消除评分流程重复，统一 run() 骨架
      │ 产出
      ▼
Adapter          各 client/provider 把异构后端适配成 ProviderRunResult
      │ 实现
      ▼
Strategy         AIProvider 接口让后端可运行时切换（含低延迟 HTTP 路径）
      │ 串联
      ▼
Chain of Resp.   HttpApi →(失败)→ Codex →(失败)→ Fallback；实时 →(失败)→ 批处理
```
